# Connect OpenClaw to Google Meet and Calendar APIs

This guide configures Google OAuth for a user-managed OpenClaw instance
running on OpenShift. It covers the API access needed to:

- find Google Meet events through Google Calendar;
- read completed conference records and artifacts; and
- export attendance, transcripts, and smart-note document bodies.

Browser-only Google Meet participation does not require this OAuth setup.
For the complete plugin reference, see the
[OpenClaw Google Meet plugin documentation][openclaw-meet].

## Before you begin

You need:

- access to a Google Cloud project;
- permission to create an OAuth client;
- the Google Meet plugin installed and enabled in OpenClaw; and
- a user-managed Claw where plugin configuration persists on its PVC.

In a Claw deployment, outbound network access and credential proxy routing
are controlled by the Claw operator. Ask the cluster administrator to verify
Google API connectivity if OAuth succeeds outside the pod but API calls fail
inside it.

## Enable the APIs

Enable these APIs in the same Google Cloud project:

- Google Meet REST API;
- Google Calendar API; and
- Google Drive API.

The Drive API is required only when exporting transcript or smart-note
document bodies with `--include-doc-bodies`.

## Create an OAuth client

Create an OAuth client with application type **Web application**.

Add this authorized redirect URI for Google OAuth Playground:

```text
https://developers.google.com/oauthplayground
```

Copy the generated client ID and client secret. Do not commit either value to
Git or paste them into chat.

For an external OAuth application in testing mode, add each Google account
that will authorize OpenClaw as a test user. Google Workspace administrators
may instead configure an internal application.

## Generate a refresh token

Open [Google OAuth Playground][oauth-playground].

1. Open the OAuth configuration panel.
1. Enable **Use your own OAuth credentials**.
1. Enter the client ID and client secret.
1. Paste the following space-separated value into
   **Input your own scopes**:

<!-- markdownlint-disable MD013 -->

```text
https://www.googleapis.com/auth/meetings.space.created https://www.googleapis.com/auth/meetings.space.readonly https://www.googleapis.com/auth/meetings.space.settings https://www.googleapis.com/auth/meetings.conference.media.readonly https://www.googleapis.com/auth/calendar.events.readonly https://www.googleapis.com/auth/drive.meet.readonly
```

<!-- markdownlint-enable MD013 -->

1. Select **Authorize APIs** and complete the Google consent flow.
1. Exchange the authorization code for tokens.
1. Confirm that OAuth Playground displays a refresh token.

The Calendar scope is read-only. The other scopes support Meet space lookup,
conference artifact access, API-created spaces, and optional document export.

## Verify the token in OAuth Playground

Before storing the refresh token, use OAuth Playground Step 3 to send:

```text
GET https://www.googleapis.com/calendar/v3/calendars/primary/events?maxResults=1
```

Require an HTTP `200` response. This proves that the access token generated by
the authorization has Calendar access.

If Google returns `SERVICE_DISABLED`, verify that the Calendar API is enabled
in the same project as the OAuth client.

## Store the OAuth configuration

Use the client ID, client secret, and refresh token from the same OAuth
Playground authorization that passed the Calendar test.

The following command reads the values without displaying them and stores the
OAuth block in the Google Meet plugin configuration:

```bash
python3 - <<'PY'
import getpass
import json
import subprocess

client_id = getpass.getpass("Google OAuth client ID: ").strip()
client_secret = getpass.getpass("Google OAuth client secret: ").strip()
refresh_token = getpass.getpass("Google OAuth refresh token: ").strip()

if not client_id or not client_secret or not refresh_token:
    raise SystemExit("All three values are required.")

patch = {
    "plugins": {
        "entries": {
            "google-meet": {
                "enabled": True,
                "config": {
                    "oauth": {
                        "clientId": client_id,
                        "clientSecret": client_secret,
                        "refreshToken": refresh_token,
                        "accessToken": None,
                        "expiresAt": None,
                    }
                },
            }
        }
    }
}

subprocess.run(
    ["openclaw", "config", "patch", "--stdin"],
    input=json.dumps(patch),
    text=True,
    check=True,
)
PY
```

This procedure is for user-managed Claws. Do not place OAuth secrets directly
in a Git-managed Claw resource or collection.

## Validate OpenClaw access

First, verify that OpenClaw can refresh the token:

```bash
openclaw googlemeet doctor --oauth --json
```

Look for `"ok": true` and `"tokenSource": "refresh-token"`.
This check confirms token refresh but does not prove that the token contains
the Calendar, Meet, or Drive scopes.

Test Calendar lookup separately:

```bash
openclaw googlemeet calendar-events --today --json
```

Or search for an event by title:

```bash
openclaw googlemeet calendar-events \
  --event "Weekly team meeting" \
  --json
```

Test completed-meeting artifact access:

```bash
openclaw googlemeet artifacts \
  --event "Weekly team meeting" \
  --json
```

## Export completed-meeting artifacts

Choose a private directory on the persistent OpenClaw volume:

```bash
EVENT_QUERY="Weekly team meeting"
OUTPUT_DIR="/home/node/.openclaw/google-meet-artifacts/weekly-team-meeting"

umask 077
mkdir -p "${OUTPUT_DIR}"
chmod 700 "${OUTPUT_DIR}"

openclaw googlemeet export \
  --event "${EVENT_QUERY}" \
  --include-doc-bodies \
  --output "${OUTPUT_DIR}"
```

The export can include:

- `summary.md`;
- `attendance.csv`;
- `transcript.md`;
- `artifacts.json`;
- `attendance.json`; and
- `manifest.json`.

Meeting exports can contain sensitive information. Do not commit them to Git,
ingest them into shared memory automatically, or expose them through a public
route.

## Troubleshooting

### OAuth doctor succeeds but Calendar returns 403

If the same authorization works in OAuth Playground but OpenClaw returns
`ACCESS_TOKEN_SCOPE_INSUFFICIENT`, compare the environments before generating
more tokens.

In an OpenShift Claw, the credential-injecting proxy may be replacing the
Google OAuth token or intercepting `*.googleapis.com` requests. This failure is
tracked in [claw-project issue #97][proxy-issue]. Proxy routes are
operator-managed; do not modify them from inside the OpenClaw pod.

### Calendar event is not found

Verify that:

- the authorized account can read the target calendar;
- the event contains a Google Meet link;
- the event title matches the `--event` query; and
- `--calendar <id>` is provided when the event is not on the primary calendar.

### Artifacts are empty

Google creates conference records and artifacts after the meeting. Wait for
processing to complete and verify that the authorized account can access the
meeting and its associated files.

### Refresh token is missing or rejected

Repeat the OAuth Playground authorization using the same client ID and secret.
Confirm that the current consent includes all required scopes and that OAuth
Playground displays a refresh token after exchanging the authorization code.

## Security checklist

- Never commit the client secret, refresh token, or access token.
- Never share an OAuth Playground link that includes credentials or tokens.
- Revoke and replace credentials that appear in chat, logs, or shell history.
- Keep exported meeting artifacts on a private persistent volume path.
- Use the narrowest scopes needed for the intended workflow.
